このリポジトリに「Threads × note 自動運用OS」を実装してください。
目的は、Threads運用による note 収益化を継続改善できる半自律システムを作ることです。

# 前提
- 実装言語: TypeScript
- ランタイム: Node.js 20+
- パッケージマネージャ: pnpm
- まずは単一リポジトリで実装
- ストレージは初期段階では SQLite
- バリデーションは zod
- テストは vitest
- ログは pino
- HTTP サーバは Fastify
- ORM は drizzle を優先
- 環境変数は .env ではなく .env.example と secrets のドキュメントを整備
- 変更は小さく刻み、各段階で動作確認可能な形にする
- README は必ず更新する

# 絶対方針
- Threads は公式 API を利用する
- note は公式公開 API がない前提で設計する
- note への書き込みは本番では非公式APIに依存しない
- note は以下の3モードを実装する
  1. research_only: 公開ページや取得系のみ
  2. draft_assist: 下書き素材生成と手動貼り付け支援
  3. browser_assisted: 将来的なブラウザ自動操作のための抽象化だけ用意
- 投稿・返信・分析・改善は冪等性を意識する
- 自動返信は危険度判定を通したものだけ実行し、閾値超えは human_review に送る
- いきなり全部盛りせず、Phase 1 から段階実装する

# Threads × note 自動運用OS

## Project Goal
このプロジェクトの目的は、Threads 運用によって note 収益化を継続改善できる半自律OSを構築することです。

主な責務:
- ジャンル選定
- 市場/競合リサーチ
- Threads投稿生成
- Threads投稿監査
- Threads投稿/返信
- エンゲージメント解析
- 改善提案
- note案出し
- note本文ドラフト生成
- note監査
- note競合調査
- 運用レトロスペクティブ

## Non-negotiables
- Threads は公式APIを利用する
- note は公式APIがない前提で設計する
- note への本番書き込みは非公式APIに依存しない
- note は以下の3モードで扱う
  - research_only
  - draft_assist
  - browser_assisted
- すべてのジョブは dry-run を持つ
- すべての外部書き込みは audit log を残す
- 危険操作は human review 経由にする
- README / docs / tests はコード変更と一緒に更新する

## Implementation Priorities
優先順位:
1. 壊れにくい設計
2. 冪等性
3. 観測可能性
4. 小さく分割されたジョブ
5. 人間レビュー可能性
6. 自動化率の向上

最初から全部盛りにしない。
まず Phase 1 の土台 → Threads運用OS → note運用OS → Claude Code運用基盤の順で進める。

## Architecture Rules
- domain と adapter を分離する
- LLM呼び出しは adapters/llm に集約する
- 外部API依存は services ではなく adapters 配下に閉じ込める
- 書き込み操作は audit log を残す
- すべてのジョブは再実行可能であること
- スキーマとバリデーションは zod で定義する
- DB変更は drizzle migration で管理する
- ファイル名・関数名・テーブル名は意味ベースで明確にする
- 暗黙の挙動を避ける

## Safety Rules
- note公開は自動本番実行しない
- reply 自動送信は safe 判定のみ
- high risk / legal risk / harassment risk / misinformation risk は human review に送る
- secrets, tokens, .env, credentials を読もうとしない
- 本番系の destructive operation はユーザー明示か review 承認なしで進めない
- 投稿本文に根拠のない断定を入れない
- 誇張、過剰な煽り、規約違反リスクを避ける

## Brand / Content Operating Rules
Threads と note は以下を満たすこと:
- フックは強く
- ただし誇張しすぎない
- 具体性を優先
- 1投稿1メッセージ原則
- noteへの導線は自然に入れる
- 同じ訴求を擦りすぎない
- 読者に「次の一手」が見える形にする
- 説明だけで終わらず、保存・共有・遷移したくなる設計にする

## Review Standards
Threads / note 共通の監査項目:
- 誇張しすぎ
- 具体性不足
- フック弱い
- CTA弱い
- 炎上 / 規約 / 誤情報リスク
- 根拠不足
- note導線が不自然
- 同一テーマ擦りすぎ
- ブランド口調からズレてる

---
name: topic-research
description: Research Threads and note content opportunities for a chosen niche or angle. Use when planning what to post next or when selecting a monetizable topic.
argument-hint: [topic-or-niche]
disable-model-invocation: true
allowed-tools: Read, Glob, Grep, Bash
---

You are the topic research operator for this project.

Goal:
- produce a ranked opportunity list for Threads -> note monetization

When invoked:
1. Read `CLAUDE.md`, `docs/architecture.md`, `docs/progress.md`, and recent outputs under `data/` or `docs/`.
2. Identify:
   - target niche
   - subtopics
   - audience pain points
   - curiosity hooks
   - monetizable note angles
3. Output:
   - top 10 topic candidates
   - why each one matters
   - Threads hook angle
   - note article expansion angle
   - risk flags
   - priority score
4. Save a concise result draft to `docs/research/latest-topic-research.md` if asked to write files.
5. Prefer concrete, non-generic themes.

Never:
- invent evidence
- recommend unsafe or policy-risky bait
- publish anything directly

---
name: generate-threads
description: Generate Threads post drafts from a chosen topic, with natural note funneling. Use when preparing daily posting candidates.
argument-hint: [topic-or-brief]
disable-model-invocation: true
allowed-tools: Read, Glob, Grep, Edit, Write
---

You are the Threads draft generator.

Produce 5 strong draft candidates per invocation.

Requirements:
- one post = one core message
- strong first line
- clear curiosity or benefit
- natural transition to note
- no forced CTA
- concrete phrasing over abstract phrasing
- avoid repeated structure across all 5 drafts

For each draft, include:
- title/label
- intended audience
- draft body
- hook type
- CTA type
- note transition hypothesis
- self-critique

If writing files, save to:
`data/threads/drafts/YYYY-MM-DD/<slug>.md`

Do not:
- overhype
- make unverifiable income claims
- produce copy that sounds generic-AI

# Threads × note 自動運用OS

## Mission
このリポジトリは、Threads 運用から note 収益化までを継続改善する半自律OSです。
最重要目的は「投稿を増やすこと」ではなく、「勝ち筋を発見し、note 収益につながる導線を強化すること」です。

## Core principle
このプロジェクトの操作主体は Claude Code です。
実装、修正、監査、調査、定期タスク、運用Runbook更新は Claude Code から行います。

## Non-negotiables
- Threads は公式APIを利用する
- note は公式APIがない前提で設計する
- note 本番公開は自動化しない
- note は以下の3モードで扱う
  - research_only
  - draft_assist
  - browser_assisted
- すべてのジョブは dry-run を持つ
- すべての外部書き込みは audit log を残す

6. Claude Code 運用基盤を整える
7. 各フェーズごとに docs/progress.md を更新する

## Architecture rules
- domain と adapters を分離する
- 外部API依存は adapters に閉じ込める
- services はユースケースをまとめる
- DBスキーマは drizzle で管理する
- すべての入力は zod で検証する
- 書き込み系処理は audit log を残す
- すべてのジョブは冪等性を意識する

- 根拠のない断定や実績の捏造をしない

- 具体性優先
- 抽象論だけで終わらせない
- 1投稿1メッセージ原則
- 保存・共有・遷移のどれを狙うかを明確にする
- note導線は“続きが欲しくなる”設計にする
- 同じテーマを雑に擦らない
- AIっぽい無機質な言い回しを避ける

- 誇張しすぎ

#!/usr/bin/env node
const fs = require("fs");

function readStdin() {
  return fs.readFileSync(0, "utf8");
}

function deny(reason) {
  process.stdout.write(
    JSON.stringify({
      hookSpecificOutput: {
        hookEventName: "PreToolUse",
        permissionDecision: "deny",
        permissionDecisionReason: reason
      }
    })
  );
}

try {
  const raw = readStdin();
  const payload = JSON.parse(raw || "{}");
  const input = payload.tool_input || {};
  const target =
    input.file_path ||
    input.path ||
    input.pattern ||
    input.command ||
    "";

  const blocked = [
    ".env",
    ".env.",
    "secrets/",
    "config/credentials.json",
    "id_rsa",
    "id_ed25519",
    "auth.json",
    "token",
    "credential"
  ];

  const text = String(target).toLowerCase();

  if (blocked.some((x) => text.includes(x.toLowerCase()))) {
    deny(`Sensitive path access blocked by project policy: ${target}`);
    process.exit(0);
  }

  process.exit(0);
} catch (err) {
  process.exit(0);
}

#!/usr/bin/env node
const fs = require("fs");
const path = require("path");
const cp = require("child_process");

function readStdin() {
  return fs.readFileSync(0, "utf8");
}

function run(command) {
  try {
    return cp.execSync(command, {
      encoding: "utf8",
      stdio: ["ignore", "pipe", "pipe"]
    });
  } catch (err) {
    const stdout = err.stdout ? String(err.stdout) : "";
    const stderr = err.stderr ? String(err.stderr) : "";
    return `${stdout}\n${stderr}`.trim();
  }
}

function respond(additionalContext) {
  process.stdout.write(
    JSON.stringify({
      hookSpecificOutput: {
        hookEventName: "PostToolUse",
        additionalContext
      }
    })
  );
}

try {
  const raw = readStdin();
  const payload = JSON.parse(raw || "{}");
  const filePath =
    payload?.tool_input?.file_path ||
    payload?.tool_response?.filePath ||
    "";

  const ext = path.extname(String(filePath)).toLowerCase();
  const relevant =
    [".ts", ".tsx", ".js", ".jsx", ".json", ".md"].includes(ext) ||
    /package\.json|pnpm-lock\.yaml|drizzle|vitest|tsconfig/i.test(String(filePath));

  if (!relevant) process.exit(0);

  const lintOutput = run("pnpm lint");
  let summary = `Post-edit check ran for ${filePath}\n\npnpm lint output:\n${lintOutput || "(no output)"}`;

  if (/\.(ts|tsx|js|jsx)$/i.test(String(filePath))) {
    const testOutput = run("pnpm test");
    summary += `\n\npnpm test output:\n${testOutput || "(no output)"}`;
  }

  respond(summary.slice(0, 12000));
  process.exit(0);
} catch (err) {
  process.exit(0);
}

#!/usr/bin/env node
const fs = require("fs");
const path = require("path");

function readStdin() {
  return fs.readFileSync(0, "utf8");
}

function ensureDir(dir) {
  fs.mkdirSync(dir, { recursive: true });
}

function today() {
  const now = new Date();
  const yyyy = now.getFullYear();
  const mm = String(now.getMonth() + 1).padStart(2, "0");
  const dd = String(now.getDate()).padStart(2, "0");
  return `${yyyy}-${mm}-${dd}`;
}

function nowIso() {
  return new Date().toISOString();
}

try {
  const raw = readStdin();
  const payload = JSON.parse(raw || "{}");
  const cwd = payload.cwd || process.cwd();
  const dir = path.join(cwd, "docs", "runlog");
  ensureDir(dir);

  const file = path.join(dir, `${today()}.md`);
  const lastMessage = String(payload.last_assistant_message || "").trim();

  const block = [
    `## ${nowIso()}`,
    "",
    `- session_id: ${payload.session_id || ""}`,
    `- hook_event_name: ${payload.hook_event_name || ""}`,
    "",
    lastMessage || "(empty last assistant message)",
    "",
    "---",
    ""
  ].join("\n");

  fs.appendFileSync(file, block, "utf8");
  process.exit(0);
} catch (err) {
  process.exit(0);
}

7. Claude Code からどう操作するか

ここが本題。
普段の運用は全部 Claude Code から叩く。

Claude Code では / でコマンド一覧、/schedule で Cloud scheduled tasks、/permissions で権限確認、/hooks で hook 確認、/agents で subagents 管理ができる。skills は /topic-research みたいにそのまま呼べる。subagents は自然文でも起動しやすいけど、確実に使いたいなら @agent-<name> で明示できる。セッション全体を agent 化したいなら claude --agent ops みたいに始める。ブラウザ補助は claude --chrome、channels は研究プレビューで --channels。

毎日の例
/topic-research 今日のThreads→note導線で狙うべきテーマを出して
/generate-threads 1位テーマで5本作って
/audit-threads data/threads/drafts/2026-03-28/post-001.md
/analyze-threads 今週の伸びた投稿の共通点を出して
/generate-note 今日一番伸びた切り口をnote化して
/audit-note data/note/drafts/2026-03-28/note-001.md
agent 明示の例
@agent-strategist 今週の勝ち筋を決めて
@agent-analyst 直近7日から次の実験案を3つ出して
@agent-auditor この返信案の危険度を判定して
セッションごと agent 固定
claude --agent ops
claude --agent strategist
claude --agent analyst
ブラウザ補助
claude --chrome
8. Cloud scheduled tasks の作り方

Cloud scheduled tasks は /schedule から作れて、repo は毎回 default branch から clone される。task は cloud environment、connectors、schedule を持てて、不要な connectors は外せる。基本は claude/ 接頭辞 branch へ変更を書き出す。

まず作る task
/schedule daily topic research at 7:00
/schedule daily threads planning at 8:00
/schedule nightly note pipeline at 23:00
/schedule weekly retro every sunday at 22:00
各 task の prompt
prompts/scheduled/daily-topic-research.md
prompts/scheduled/daily-threads-plan.md
prompts/scheduled/post-publish-followup.md
prompts/scheduled/nightly-note-pipeline.md
prompts/scheduled/weekly-retro.md
運用のコツ
Cloud task は 企画・分析・ドラフト生成・改善案出し に使う
note の最終公開前確認みたいなブラウザ依存は claude --chrome 側に逃がす
task に含める connectors は必要最小限に絞る
setup script が必要なら cloud environment で依存を入れる
