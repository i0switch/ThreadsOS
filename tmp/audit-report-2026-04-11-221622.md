## 全体サマリー

### 総評

現状の ThreadsOS は、毎時ハートビートを中心に、部署別レポート収集、エグゼクティブ判断、Threads と note の自動生成・自動公開、反応分析、価格調整、提案管理、ダッシュボード監視までかなり広く実装されています。特に、src/jobs/hourly-heartbeat.ts、src/services/executive/index.ts、src/services/department-execution/index.ts、src/services/auto-publisher/index.ts をつないだ実行ループは、仕様の中核にかなり近いです。

一方で、仕様本文の中でもっとも強い文言である「テーマ・資料だけ渡せば、以降すべて自律継続」という最終定義は現実装と一致していません。現状は src/cli/setup.ts で Threads トークン設定が必要で、既定セットアップでは src/cli/note-login.ts による note セッション保存も必要です。ただしコード上は NOTE_SESSION_COOKIE を使う代替認証経路もあります。さらに note ヘッダー画像は src/services/department-execution/index.ts の thumbnailTasks 経由で人手作業として残っています。なお、仕様内には「ユーザーはテーマ・資料だけ」と「ユーザーはアカウント設定とヘッダー追加も行う」が同居しているため、本レポートではその矛盾を解消せず、文言どおり別要件として監査しています。

### 実装済みの中心領域

- 毎時ハートビートを軸にした実行フロー
- エグゼクティブによる部署横断判断と部署実行
- Threads 投稿生成、公開、反応取得、返信判定と安全返信
- note 記事生成、公開、公開後分析、価格決定
- 競合スナップショット保存基盤、競合分析、部署間通知
- ダッシュボードによる監視、提案承認、停止再開

### 弱い領域

- テーマと資料だけで運用開始できるという最終定義
- ループ実行とデスクトップアプリのスケジュール機能
- 自己拡張としてのスキル・プラグイン調査導入
- Threads 向け競合リサーチの収集経路と部署内実行配線
- Threads から note への流入と収益化の実測 attribution

### 未実装の大項目

- ハートビート本体のループ実行
- デスクトップアプリのスケジュール機能
- スキル・プラグインの自動調査導入
- スキル・プラグインの自動生成実装

## 次フェーズで改修が必要な項目

### 優先度高

- 「テーマ・資料だけで以降自律」と現実装の差分解消
- Threads から note への実流入と収益化 attribution の実測化
- ハートビート本体のループ実行の追加、または仕様からの明示削除
- デスクトップアプリのスケジュール機能の実装、または仕様修正
- スキル・プラグインの自動導入、自動実装要件の扱い整理

### 優先度中

- Threads 向け競合収集経路の追加と、Threads 部署内の競合リサーチ係の実行パス接続
- 外部リサーチ部署の市場動向把握とジャンル理解更新を専用ロジック化
- 管理・指揮系統が返信内容と生成内容に直接介入する仕組みの強化
- 方針調整を objective と funnelStage 以外の policy へ拡張

### 優先度低

- 1時間に1回をアプリ内部でも保証する仕組みの追加
- note ヘッダー画像タスクの完了導線の明確化
- 仕様本文内の重複と矛盾の整理
