# ThreadsOS ダッシュボード監査

監査日時: 2026-04-11 22:17:53

前提:
- コード編集は行っていない。
- 監査対象の主軸は src/dashboard/public/index.html、src/dashboard/routes.ts、src/services/dashboard-query/index.ts、および関連する state / schema / test 実装。
- 判定区分は 実装済み / 一部実装 / 実装はあるが要件ズレ / 未実装 の4区分で固定した。

## 総評

現在のダッシュボードは、単なる監視画面からはかなり離れており、AI組織の流れ・人の確認待ち・Threads→note 導線を見せようとする意図は明確に実装されている。特に、トップの確認待ち導線、AIチームのストーリーボード、Threads→note ファネル、右側の詳細パネル、詳細データの折りたたみは、初心者向けに寄せようとした設計として評価できる。

ただし本質的には、まだ 物語化した運用コンソール であり、初心者向け販売アプリとしての直感性には届いていない。理由は、今何が起きているか、今何を判断すべきか、売上導線のどこが詰まっているか、が単一の主導線に統合されず、ホーム、確認待ち、タイムライン、判断履歴、成果欄に分散しているためである。さらに主画面向け API 構造は画面セクションごとに分かれており、補助 API も別系統で併存しているため、同種の集約データを複数回生成している。

## 現在のダッシュボードの本質的な問題

1. 画面の見た目はストーリー寄りだが、データ構造と取得方式は依然として機能別のまま。
2. 現在地、次の人間判断、次の AI 行動、収益導線の詰まり、が単一の主画面状態としてまとまっていない。
3. 初心者向け文言に寄せる変換層はあるが、ハートビート、管理者メモ、scope、target、agentId、KPI JSON など内部運用語が残っている。
4. 可視セクションだけ更新しているという表現に対して、実際は15秒ごとの refresh ループの上で主要6セクションを60秒または90秒単位で定期更新しており、更新抑制は限定的。
5. request-scoped cache はあるが、HTTP リクエストをまたいだ重複集約は抑えられていない。

## 良い点

1. あなたの確認待ちがホーム内でも独立セクションでも強く前面化されている。
2. Threads と note を separate metrics ではなく funnel として見せる専用面がある。
3. AI の判断根拠、判断、実行内容、期待結果を detail panel で読める。
4. KPI / ログ / 予算を既定で閉じ、通常運用の主画面から退避している。
5. 右側の固定詳細パネルにより、一覧から詳細へ遷移しても文脈を失いにくい。

## 初心者向けとして弱い点

1. 一番知りたい 今の状況 と 今の判断 を複数セクションから自力で統合する必要がある。
2. AI組織の説明はあるが、初心者の頭の中にある 売上 / 集客 / 詰まり / 次の確認、という販売アプリのメンタルモデルにはまだ寄っていない。
3. 一部 UI 文言と入力欄が内部運用者向けの言葉のまま残っている。
4. タイムラインが人間・AI・システムを混在表示し、管理者の行動追跡としてはやや散る。
5. 動的に存在する部署すべてを storyboard で見せているわけではない。

## 最優先で直すべき点

1. 今何が起きているか / 今何を判断するか / 収益導線のどこが詰まっているか を1つの主導線として整理すること。
2. セクション分割 API と常時ポーリングにより起きている重複集約を見直すこと。
3. 初心者に不要な内部運用語と生データ表現をさらに減らすこと。

要件番号: 12
要件: summary などのデータ取得が重複しすぎていない

根拠:

1. 画面全体としては同種 aggregate を複数 API で何度も再生成している。

## 情報設計の問題まとめ

### 情報の優先順位

1. あなたの確認待ちの優先順位づけ自体は強い。
2. ただし 現在地、止まり、判断、成果、履歴 が home / timeline / decisions / results に分散し、2位以下の優先順が曖昧。
3. 初心者向け販売アプリなら、今の判断、今の詰まり、今の売上導線、の順で一本化されるべきだが、現状は複数面へ散る。

### 導線

1. 一覧→詳細の導線は良い。
2. ただし トップ把握→判断→実行結果確認 の一本導線より、複数カードを横断して理解する導線になっている。
3. 管理者履歴も追えるが、人間イベント専用の見方は弱い。

### 文言

1. 文言の平文化はかなり入っている。
2. それでも heartbeat、scope、target、agentId、metrics JSON など内部語が残る。
3. 初心者向け販売アプリとしては、売上・集客・記事・確認・停止理由 などの即理解語にさらに寄せる余地が大きい。

### 自動更新

1. ブラウザタブ非表示時停止と詳細面の遅延取得は良い。
2. しかし主要6面に対する定期更新ループがあり、各 source の interval は 60秒または90秒で、不要箇所抑制としては不十分。
3. UI 上の 可視セクションだけ更新 という表現を完全には裏づけていない。

### API構造

1. 主画面の UI セクションごとに API が切られており、意味別ラベルに対して取得粒度は機能別。
2. getSummary、getDepartments、getDepartmentDetail、getDashboardInbox などの集約が複数 API から再利用されるため、サーバー側計算の重なりが多い。
3. request-scoped cache は設計として正しいが、画面全体最適化としては不足。

### 初心者理解の阻害要因

1. AI組織の内部構造が強く見え、販売アプリとしての問いに対する答えが一撃で出ない。
2. タイムラインが人間・AI・システム混在で、管理者の行動追跡として読むにはノイズがある。
3. storyboard が動的な全部署ではなく固定 blueprints 中心。
4. 詳細データ面は raw 表現が残り、初心者向けではない。
